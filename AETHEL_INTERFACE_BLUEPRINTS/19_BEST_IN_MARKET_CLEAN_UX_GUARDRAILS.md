# 19_BEST_IN_MARKET_CLEAN_UX_GUARDRAILS
Date: 2026-04-29
Status: BLUEPRINT
Surface Type: Cross-Surface UX Guardrail

## Purpose
Prevent Aethel from drifting into:
- generic AI app screens,
- noisy dashboard layouts,
- weak preview/chat side-by-side compromises,
- or shallow Firebase-like simplicity that erases Studio depth.

This is the anti-demo document.
It defines what must be true if the product is going to feel as clean as the best products in market while remaining more powerful than them.

### Canonical takeaway
Firebase is a strong reference for:
- entry simplicity,
- mission clarity,
- and low-anxiety web onboarding.

Firebase is not sufficient for:
- artifact-first review,
- dense Studio work,
- browser operator governance,
- or local-depth workflows.

## Core Anti-Generic Rules

### Rule 1: One dominant surface per screen
Every major surface must have one obvious protagonist.

Allowed examples:
- Home -> mission input
- Studio Home -> mission hero
- Operator -> browser canvas
- Workbench -> editor or viewport
- Preview Review -> artifact

If three areas compete equally, the screen becomes generic.

### Rule 2: Text must explain less than structure proves
Do not solve ambiguity with paragraphs.
Solve ambiguity with:
- hierarchy,
- affordances,
- state grammar,
- and correct grouping.

### Rule 3: Avoid equal-weight card fields
Generic products make every card feel equally important.
Best-in-market products establish:
- one main object,
- one support rail,
- one action area,
- one secondary information basin.

### Rule 4: Preview and chat must not become roommates
Default 50/50 preview + chat is one of the most common weak AI-builder patterns.

Aethel rule:
- preview dominates when the decision is visual
- editor dominates when the task is implementation
- chat compresses into an operational rail

### Rule 5: Simplicity at entry cannot erase depth later
The user should feel:
- simpler first,
- deeper later,
- never disconnected.

If Web Light and Studio feel like different products, the design fails.

## Surface-Specific Guardrails

### Home / Web Light
Must feel:
- like an AI app
- immediate
- low-anxiety
- clean

Must not feel:
- like a SaaS marketing page
- like a dashboard
- like a chat clone

Must contain:
- one mission input
- one short headline
- one support sentence
- starting chips
- domain triage
- recent mission continuation
- small Studio proof

Must avoid:
- big feature grids
- paragraphs
- too many CTAs
- heavy nav

### Studio Home
Must feel:
- like a control room
- like a continuity layer
- like a current-task surface

Must not feel:
- like admin analytics
- like tab clutter
- like a mini IDE

Must contain:
- mission hero
- next action
- approvals / blockers
- active run state
- evidence / outputs
- budget / trust summary
- Open in Studio

Must avoid:
- ten cards at equal visual weight
- separate AI chat area as a primary object

### Workbench / Studio Cloud
Must feel:
- serious
- inevitable
- professional
- artifact-first

Must not feel:
- like dashboard leftovers
- like several shells glued together
- like chat with an editor attached

Must contain:
- one shell grammar
- one dominant work surface
- operational AI rail
- serious preview/review
- diagnostic basin

Must avoid:
- preview being a widget
- AI being only a sidebar conversation

### Studio Local
Must feel:
- like the same Studio
- just deeper and more trusted

Must not feel:
- like another desktop app brand
- like a fork with different IA

Must contain:
- same shell grammar
- same mission objects
- same state language
- local-depth affordances only where needed

### Operator Surface
Must feel:
- like governed execution
- like real work on the internet
- like a browser with accountability

Must not feel:
- like hidden magic
- like a generic automation bot

Must contain:
- browser canvas
- plan
- approvals
- evidence
- action ledger
- takeover controls

## Visual Cleanliness Rules

### Spacing
- prefer fewer, stronger groups
- use whitespace to define levels, not emptiness
- avoid stacked banners

### Typography
- one strong headline per surface
- one smaller support layer
- operational labels must stay compact

### Color
- status color means status only
- avoid decorative saturation
- deep dark surfaces must stay calm, not neon

### Borders and cards
- cards should define function, not existence
- if a card has no unique job, it should become part of another block

## Robustness Signals
To avoid looking like a demo, surfaces should visibly support:
- progress
- approvals
- rollback
- evidence
- trust
- cost
- continuity

If the UI only shows:
- prompts
- outputs
- nice cards

it will still feel like a demo.

## Benchmark Fusion Rule
Aethel should feel:
- Firebase-like at entry
- Manus-like in operator usefulness
- ChatGPT/Gemini-like in low-friction asking
- Cursor/Windsurf-like in AI + implementation depth
- Vercel-like in preview/review trust
- Unreal-like in viewport authority

But it must reject:
- Firebase shallowness
- Manus opacity
- chat-first sprawl
- Unreal entry heaviness

## Final Reading
The correct Aethel UI is not maximal.
It is disciplined.

It wins by:
- showing less,
- meaning more,
- revealing depth at the right moment,
- and keeping one product identity from first prompt to deepest Studio session.
