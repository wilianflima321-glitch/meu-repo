# Viewport Runtime Boundaries

Generated by: `qa:viewport-runtime-boundaries`

## Decision

The viewport is the most expensive visible surface in Aethel. It should feel instant around the chrome, cost meter, runtime selector, and evidence UI, then load the browser scene only when the Browser runtime is actually selected.

## What is protected

- Browser runtime canvas is lazy: `AethelViewport3D` dynamically loads `ViewportSceneCanvas`.
- Camera presets are lightweight: `VIEWPORT_CAMERA_PRESETS` and `ViewportCameraPreset` live in `viewport-camera-presets.ts`, so toolbar chrome does not import R3F or Three.
- Viewport model is isolated: seed objects and public viewport contracts live in `viewport-model.ts`, keeping the orchestrator under the 350-line contract.
- Runtime depth status is isolated: Browser/Studio Local/Cloud Stream status rendering lives in `ViewportRuntimeDepthStatus`.
- Transform gizmo runtime stays inside the scene boundary.
- GameViewport stays dynamic through `VRPreview` and is marked as a heavy async boundary.

## Product rule

No public route can import the browser runtime scene directly. Public pages can explain Browser, Studio Local, and Cloud Stream, but the R3F canvas belongs behind Studio/preview intent.

## Market critique

Unreal and Unity can afford heavy native startup because users expect an editor. Aethel is browser-first; the shell must respond like Linear/Vercel while still opening into engine depth when asked. This boundary keeps that promise honest.
